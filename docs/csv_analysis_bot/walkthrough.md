# 壁打ち結果・設計完了ウォークスルー (walkthrough.md)

## 1. 概要
ユーザー様との「売上伝パー・共起分析ベースの行動指示自動生成ツール」に関する壁打ちセッションを実施し、要件整理・多用途展開のアイデア検証・懸念点抽出・工期見積もりを完了しました。

壁打ちで確定した内容に基づき、プロジェクトの全体設計およびタスクリストを `docs/csv_analysis_bot/` 配下に格納・作成しました。

---

## 2. 壁打ちによる決定事項・ハイライト

1. **プロダクト核概念の確定**
   - BIツール/AIのようなグラフ可視化ではなく、「明日のアクション（営業のカンペ）」をダイレクトに出力する完全オフラインデスクトップアプリ。
2. **多用途展開（マルチプリセット）の採用**
   - コアとなるRust解析エンジンは `(GroupID, ItemID)` の抽象共起分析として設計。
   - CSVとプリセット選択により、以下4つの用途を1つのアプリでガシャンと切り替え可能に決定。
     1. 売上・ついで買い提案（営業向け）
     2. 倉庫のピッキング動線最適化（物流向け）
     3. 不良品・機械トラブルの原因特定（製造向け）
     4. 業務システムの隠れた使い方分析（IT改善向け）
3. **アドオン（プラグイン）拡張アーキテクチャの採用**
   - 将来的な分析アルゴリズム（RFM分析や需要予測など）の追加要望に対し、アプリ本体のリビルドなしで対応できるよう、WASMまたはCLIベースのアドオン機構を導入することで合意。これによりSIカスタマイズ案件の開発工数を劇的に削減。
4. **懸念点と対応方針の整理**
   - CSV表記揺れ/文字コード ➔ 自動判別 ＋ 列マッピング画面の用意
   - 匿名IDの使いにくさ ➔ ローカル保存マスターCSVの任意名寄せ機能
   - Windowsセキュリティ警告 ➔ コード署名 ＆ 正規インストーラー作成
5. **工期見積もり**
   - デモ版（PoC）＋ プリセット汎用化対応（アドオン機構含む）で **全工程 約2.75ヶ月（約55営業日）** と算出。

## 4. 次のアクションアイテム
1. **アプリ骨格（スカフォールド）の作成 [完了]**
   - Tauri (Vanilla TS + Vite + Rust) のベース環境を `./app` 配下に生成し、アドオン用の `plugins/` ディレクトリを整備しました。
2. **Phase 1: Rustコアエンジンのプロトタイプ実装 [コード実装完了]** 
   - `sample_sales.csv`（ダミー売上データ）を自動生成しました。
   - `src-tauri/src/lib.rs` に、高速CSVパース処理と、商品の同時購入確率（支持度・信頼度）を算出する共起分析ロジックを実装しました。
   - UI (`index.html`, `main.ts`) から `invoke("analyze_csv")` を呼んで結果を受け取る処理を実装しました。
   - *(※現在のサンドボックス環境では `pkg-config` や `webkit2gtk` といったLinux用のTauri開発依存パッケージが不足しているためビルドはスキップしています。)*

3. **ローカル起動成功 ＆ Phase 2 移行 (Next):** 
   - 依存パッケージのインストール完了後、`npm run tauri dev` で無事にアプリが起動し、RustからのJSON出力（支持度・信頼度の計算結果）が得られることを確認しました。
4. **Phase 2: UI構築 ＆ カンペテンプレートエンジンの実装 [完了]** 
   - 画面を「左ペイン（設定）」と「右ペイン（カンペリスト）」の2つに分割し、直感的な操作が可能なワイヤーフレームを実装しました。
   - `styles.css` にて Glassmorphism（すりガラス風）を採用し、モダンでリッチなダークテーマUIを構築。ホバー時のアニメーションも加えました。
   - `main.ts` のテンプレートエンジンをアップデートし、「🎯 アクション（行動指示）」と「💡 解説（データ的根拠）」を明確に分離したレイアウトに変更。専門用語（確率など）を解説側に押し込むことで、一般の営業担当でも「次に何をすべきか」が一目でわかるようにしました。
   - サンプルデータを拡張し、100%だけでなく様々な確率（80%や66%など）がリアルに出るように調整しました。
   - **【機能強化】**Rustの分析エンジンを調整し、「プリンタ→インク」と「インク→プリンタ」のように両方向のルールが生成される場合、より確率の高い一方向（自然な提案方向）のみをカンペとして採用するようにロジックを修正しました。
